# OWASP Top 10:2025 code review checklist

For each category: where to look, starting points for search, the questions that decide
whether there is a finding, and the usual fix. Grep patterns are starting points to find the
right files, not detectors. Trace data flow before reporting.

## A01 Broken Access Control

Look at: route definitions, middleware/guards/policies, controllers that load records by id,
admin routes, file download endpoints, GraphQL resolvers, multi-tenant query helpers, outbound
HTTP calls built from user input (SSRF).

Search: `params.id`, `req.params`, `findById`, `get_object_or_404`, `/:id`, `@PathVariable`,
`->find(`, `role`, `isAdmin`, `tenant`, `owner`, `fetch(`, `requests.get(`, `curl_init`.

Questions:
- Is every route authenticated unless explicitly public? Is the default deny?
- For each record loaded by id: is it scoped to the current user/tenant in the query itself
  (`WHERE id = ? AND owner_id = ?`), not checked after the fact or only in the UI?
- Can a normal user call admin endpoints or change `role`, `is_admin`, `tenant_id`, `price`
  through mass assignment (request body bound straight to the model)?
- Are authorization checks the same for every method (GET/PUT/DELETE) and every representation
  (REST, GraphQL, export/CSV, websocket)?
- CORS: does it reflect arbitrary origins with credentials?
- SSRF: can the user control a URL/host the server fetches (webhooks, URL previews, image
  import, PDF renderers)? Are private, loopback and link-local (cloud metadata) addresses
  blocked after DNS resolution and on every redirect?
- Directory/file access: can a path parameter escape the intended directory?

Fix: centralised policy checks (Pundit/CanCan, Django permissions, Laravel policies, Spring
`@PreAuthorize`, NestJS guards); scope queries by owner/tenant; allow-list bindable fields
(DTOs, `$fillable`, serializers with explicit fields); deny by default; tests that call each
endpoint as another user and expect 403/404. For SSRF: allow-list destinations, resolve and
check IPs, disable redirects or re-check them, run fetchers without metadata access.

## A02 Security Misconfiguration

Look at: framework settings (`settings.py`, `.env.example`, `config/*.php`, `application.yml`,
`appsettings.json`), web server config, Dockerfiles, CORS setup, error pages, default accounts,
cloud storage ACLs in IaC.

Search: `DEBUG`, `APP_DEBUG`, `display_errors`, `stacktrace`, `cors(`, `Access-Control-Allow-Origin`,
`allowed_hosts`, `ALLOWED_HOSTS = ['*']`, `public-read`, `admin:admin`, `actuator`, `/debug`,
`phpinfo`, `swagger`.

Questions:
- Is debug mode off in production, and does an error return a stack trace or SQL to the client?
- Are admin consoles, metrics, Swagger, actuator, phpMyAdmin exposed without auth?
- Are security headers set (run `security-headers-check`)? Are cookies flagged
  (`auth-session-review`)?
- Are XML parsers configured without external entities? Are directory listings off?
- Are sample apps, default credentials and unused features removed?
- Are containers non-root with pinned images (`dockerfile-security`)?

Fix: environment-specific config with secure production defaults, a hardening checklist in
deploy, automated header/config checks in CI.

## A03 Software Supply Chain Failures

Look at: lockfiles, package manifests, CI workflows (`.github/workflows`, `.gitlab-ci.yml`),
install scripts, Docker base images, vendored code, CDN `<script>` tags.

Search: `postinstall`, `curl | sh`, `uses: .*@(main|master|v\d+)$`, `pull_request_target`,
`<script src="https://`, `--extra-index-url`, `git+https`.

Questions:
- Are dependencies locked and installed from the lockfile (`npm ci`, `pip install --require-hashes`,
  `composer install`)? Run `dependency-audit` for known vulnerabilities.
- Are abandoned or unmaintained packages in use? Are there typosquat-looking names?
- CI: are third-party actions pinned to a commit SHA? Does `pull_request_target` or a
  self-hosted runner run untrusted fork code with secrets? Are tokens least-privilege
  (`permissions:` set)?
- Do third-party scripts from CDNs use Subresource Integrity (`integrity=`)?
- Could a private package name be resolved from the public registry (dependency confusion)?

Fix: lockfiles + automated updates (Dependabot/Renovate) + audit gate, pin actions by SHA,
minimal CI permissions, SRI, scoped registries for private packages.

## A04 Cryptographic Failures

Look at: password storage, token generation, encryption helpers, TLS settings, config for
data at rest, places that handle PII/payment data.

Search: `md5`, `sha1`, `sha256(` near password, `Math.random`, `random.random`, `rand(`,
`mt_rand`, `uniqid`, `AES/ECB`, `DES`, `RC4`, `verify=False`, `rejectUnauthorized: false`,
`InsecureSkipVerify`, `CURLOPT_SSL_VERIFYPEER`, hard-coded `iv`/`key`.

Questions:
- Passwords: Argon2id, scrypt, bcrypt or PBKDF2 with modern parameters? (See
  `auth-session-review` references.) Never plain hashes or reversible encryption.
- Tokens (reset, session, API keys, invite links) from a CSPRNG (`secrets`, `crypto.randomBytes`,
  `random_bytes`, `SecureRandom`) with at least 128 bits?
- Encryption: authenticated modes (AES-GCM, ChaCha20-Poly1305) via a vetted library; unique
  nonces; keys from a KMS/secret store, not code?
- Is TLS certificate verification ever disabled? Is sensitive data sent over HTTP or put in URLs?
- Is sensitive data stored that does not need to be (full card numbers, raw ID documents)?

Fix: use the platform's high-level APIs (libsodium, `cryptography` Fernet/AESGCM, Web Crypto,
Tink), rotateable keys in a KMS, data minimisation.

## A05 Injection

Look at: database access, shell commands, template rendering, HTML output, LDAP/XPath queries,
deserialization, dynamic code. Run `input-validation-review` for the sink list and safe patterns.

Questions:
- Is every query parameterized, including ORDER BY / column names (allow-list those)?
- Does any raw query helper (`raw`, `extra`, `knex.raw`, `$queryRawUnsafe`, `DB::raw`) receive
  user input?
- Is user input ever passed to a shell, `eval`, template compilation, or a deserializer?
- XSS: is template auto-escaping on everywhere? Where is it bypassed (`|safe`, `{!! !!}`,
  `dangerouslySetInnerHTML`, `v-html`, `innerHTML`)? Is the right context escaping used (HTML
  attribute, URL, JS)?
- Are file names, headers (CRLF) and log lines built from input?

Fix: parameterized APIs, argument arrays without a shell, auto-escaping + sanitizer (DOMPurify,
bleach-like allow-lists) only where HTML is required, CSP as defence in depth.

## A06 Insecure Design

Look at: business flows - signup, checkout, coupons, transfers, invitations, password reset,
file sharing, rate-sensitive operations.

Questions:
- Can a step be skipped or replayed (pay once, ship twice; reuse a coupon; race two requests)?
- Are limits enforced server-side (quantity, price, balance, number of attempts, file size)?
- Is there rate limiting or anti-automation on expensive or abusable actions (login, SMS,
  email, search, exports)?
- Is there a threat model for the feature? If not, run `threat-modeling` on it.
- Do trust boundaries hold - e.g. a "public" microservice that trusts an `X-User-Id` header?

Fix: server-side state machines, idempotency keys, transactions/locks for balance changes,
quotas, abuse-case tests.

## A07 Authentication Failures

Look at: login, signup, password reset, MFA, remember-me, session handling, SSO/OAuth callback,
API key handling. Use `auth-session-review` for the detailed checklist and cookie/JWT scripts.

Questions:
- Is there brute-force protection (per account and per IP) and credential-stuffing defence?
- Are password rules sensible (length >= 8 with MFA or >= 15 without, breached-password check,
  no forced composition rules)?
- Reset tokens: random, single use, short-lived, invalidated on use and on password change? No
  user enumeration through different responses or timing?
- Is the session ID rotated at login and privilege change, invalidated at logout and on
  password change?
- OAuth/OIDC: `state` and PKCE used, redirect URIs exact-match, ID token audience/issuer verified?

Fix: framework auth components, MFA (WebAuthn/passkeys preferred), uniform error messages,
session regeneration, secure cookie flags.

## A08 Software or Data Integrity Failures

Look at: deserialization of untrusted data, auto-update mechanisms, webhooks, signed URLs,
client-side trusted data (prices, roles in hidden fields or unsigned cookies), CI/CD artifact flow.

Questions:
- Are incoming webhooks verified (HMAC signature, timestamp tolerance, replay protection)?
- Does the app trust data the client could change (hidden form fields, local storage, unsigned
  JWT/cookie claims, `alg: none`)?
- Is anything deserialized with pickle/Java serialization/PHP `unserialize` from outside?
- Are build artifacts and container images signed or at least produced only by CI?

Fix: verify signatures with constant-time comparison, keep authoritative state server-side,
JSON with schema validation, artifact signing (Sigstore/cosign) and provenance.

## A09 Security Logging and Alerting Failures

Look at: logging config, auth/authorization code paths, audit tables, alerting rules.

Questions:
- Are logins (success/failure), MFA changes, password resets, permission changes, access
  denials and admin actions logged with user id, IP, timestamp and request id?
- Are secrets, tokens, passwords and full card numbers kept out of logs?
- Is log input neutralised (newline/CRLF injection)?
- Would anyone be alerted to 100 failed logins per minute or a spike in 403s? Who?
- Are logs retained long enough and protected from tampering?

Fix: a structured security event logger, redaction filters, alerts on auth anomalies,
retention policy.

## A10 Mishandling of Exceptional Conditions

Look at: `try/catch` blocks around auth and payment logic, error handlers, timeouts, retries,
resource limits, parsing of unusual input.

Search: `catch (`, `except:`, `except Exception: pass`, `rescue => e`, `recover()`, `@SuppressWarnings`,
`finally`, `timeout`, `ignore_errors`.

Questions:
- Does any error path fail open (exception in the permission check means "allowed"; signature
  verification error ignored; payment status unknown treated as paid)?
- Are exceptions swallowed silently where they should stop the operation?
- Do error responses leak internals (stack traces, SQL, file paths, versions)?
- Are partial failures rolled back (transactions), and are retries idempotent?
- Are there limits and timeouts for large/odd input (huge JSON, deep nesting, zip bombs, slow
  clients)?

Fix: fail closed, catch specific exceptions, generic client errors with a correlation id,
transactions, timeouts and size limits, tests for error paths.
